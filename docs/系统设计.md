## 1 项目概述

### 1.1 要解决的问题

需要在一个**无市电、无光纤、手机信号不稳定**的环境中，监测三路环境参数并集中显示：

| 参数 | 传感器 | 说明 |
|---|---|---|
| 雨情 | 雨滴传感器 | 判断无雨/小雨/中雨/大雨 |
| 水位 | XPT2046 液位转换板 | 0~90mm，百分比显示 |
| 温湿度 | DHT20 | 温度 ℃ / 湿度 %RH |

测点与观察点相距数十米以上，拉线不现实，因此采用 **LoRa 私有无线链路**。

### 1.2 为什么选 LoRa 而不是 WiFi/蓝牙

| 方案 | 距离 | 功耗 | 穿墙 | 结论 |
|---|---|---|---|---|
| WiFi (ESP8266) | ~50m | 高（峰值 200mA+） | 差 | 距离不够，且需 AP |
| 蓝牙 | ~10m | 低 | 差 | 距离太短 |
| **LoRa 470MHz** | **数百米~公里级** | **低（发射 ~100mA 瞬时）** | **较好** | **选用** |

LoRa 的关键优势是**接收灵敏度高**（可到 -148dBm），在低速率下能用很小功率实现远距离。

### 1.3 双机角色划分

| | 从机（Slave） | 主机（Master） |
|---|---|---|
| **角色** | 发送端 / 感知节点 | 接收端 / 汇聚显示 |
| **职责** | 采集传感器 → 组帧 → LoRa 发送 | LoRa 接收 → 拼帧 → 解析 → 显示 + 报警 |
| **传感器** | 雨滴 + 水位 + DHT20 | 无 |
| **显示** | 本地串口（调试） | OLED 128×64 |
| **报警** | 无 | 蜂鸣器（水位 > 70%） |
| **上报周期** | 1 秒 | — |
| **屏幕刷新** | — | 10 秒（报警例外，立即） |

> 两台板子硬件相同（都是 STM32F103ZET6 开发板），只是**烧录的固件不同**。

## 3 通信链路

### 3.1 LoRa 参数（双端必须完全一致）

| 参数 | 值 | 来源 |
|---|---|---|
| 模块型号 | AS32-TTL-100-C | — |
| 地址 | `0x0000` | `main.c` 配置 |
| 信道 | `0x3D`（471MHz） | `lora_as32.h` → `LORA_DEFAULT_CHAN` |
| 串口波特率 | 9600 8N1 | `main.c` → `LORA_BRR` |
| 空中速率 | 2.4 kbps | `LORA_AIR_SPEED_2K4` |
| 传输模式 | 透明传输 | `LORA_OPTION_TRANSPARENT` (0x40) |

**配置写入流程**（两机相同）：

```c
config.addh   = 0x00;
config.addl   = 0x00;
config.speed  = LORA_UART_8N1 | LORA_UART_BAUD_9600 | LORA_AIR_SPEED_2K4;
config.chan   = LORA_DEFAULT_CHAN;
config.option = LORA_OPTION_TRANSPARENT;
LORA_SetConfig(&config);
```

> **注意型号差异**：AS32-TTL-100-C 出厂信道是 **0x3D（471MHz）**，
> 而 AS32-TTL-100 是 **0x17（433MHz）**，两者不通用，混用收不到。

### 3.2 链路耗时估算

从机单次上报的耗时构成（用于判断 1 秒周期是否可行）：

| 环节 | 耗时 | 依据 |
|---|---|---|
| 雨滴 AO 采样（10 次 + 5 次自检） | ~1 ms | 每次采样 50µs 间隔 |
| 水位采样（10 次 + 5 次自检） | ~2 ms | ADC 转换 + 200µs 间隔 |
| DHT20 单次测量 | ~100 ms | 含 80ms 测量等待 |
| LoRa 发送 71 字节 @9600 | ~74 ms | 71 × 10bit / 9600 |
| **合计** | **~200~250 ms** | |

**结论**：1 秒周期余量约 750ms，安全。**不要低于 500ms**，否则 DHT20 来不及。

### 3.3 为什么不加应答重传

| 方案 | 代价 | 收益 |
|---|---|---|
| 加 ACK + 重传 | 主机需回发，从机需开接收窗 → 功耗上升；协议复杂度翻倍 | 可靠性提升 |
| **不加（当前）** | 丢帧就丢一帧，1 秒后自然补上 | **简单，功耗低** |

理由：**数据是周期性重复采集的**，丢一帧的损失是 1 秒的数据空白，而下一帧马上就到。
相比"保证每帧都到"的复杂度，**用周期性冗余换取简单性**更划算。

坏帧由校验和丢弃，不会污染显示。

## 4 关键设计：LoRa 分段吐数据与流式拼帧

**这是本项目最重要、最容易踩的坑。**

### 4.1 问题现象

主机屏幕一直显示 `温度:--`，但串口明明收到了数据。

### 4.2 实测日志

主机串口打印（同一毫秒级连续到达）：

```
[RX] $RAIN,DHT20,T=26.5,H=52.2,A        ← 32 字节
DC=4092,V=3297,WET=0,DO=1,LEVEL         ← 32 字节
[RX] =0,WL=80*8B                         ← 7 字节
```

完整一帧应该是 71 字节：

```
$RAIN,DHT20,T=26.5,H=52.2,ADC=4092,V=3297,WET=0,DO=1,LEVEL=0,WL=80*8B
```

### 4.3 根因

**AS32-TTL-100-C 模块通过空口收到一包数据后，不是一次性吐到串口，而是按 32 字节一块分块输出。**

块与块之间串口会短暂空闲（≥1 字符时间），触发 STM32 的 **IDLE 中断**。

原代码逻辑：

```c
if (USART3_TakeFrame(buf, &len)) {     // 每次 IDLE 都取走
    Master_ParseFrame(buf, len);        // 拿到的是 32 字节碎片
}
```

碎片里找不到完整帧头 + 校验和 → `Master_ParseFrame()` 必然返回 0
→ `master_data` 从未被填充 → 屏幕显示 `温度:--`。

### 4.4 解决方案：流式拼帧器

`code/master/user/api/frame_assembler.c`

```
收到碎片 ─► 追加到缓冲 ─► 扫描 '\n'
                            │
              ┌─────────────┴─────────────┐
              │ 找到                        │ 没找到
              ▼                             ▼
        切出一整行                    等后续碎片
              │
              ▼
    行首是 '$' ？ ──否──► 丢弃（残留垃圾）
              │是
              ▼
        输出给解析器
```

主循环用法：

```c
while (FrameAsm_Push(&s_frameAsm, s_rxBuf, rxLen,
                     s_frameBuf, sizeof(s_frameBuf), &frameLen))
{
    if (Master_ParseFrame(s_frameBuf, frameLen)) {
        showingWait = 0;
        screenDirty = 1;
    }
    rxLen = 0;   // 后续数据已在缓冲里，继续扫
}
```

### 4.5 三个关键防护

| 防护 | 作用 | 不做的后果 |
|---|---|---|
| **行首必须是 `$`** | 挡住 `=0,WL=80*8E` 这种半截残留 | 残帧和新帧粘连，解析全失败 |
| **缓冲内无 `$` 即清空** | 垃圾流等不到换行会堵死缓冲 | 后续正常帧永远拼不出来（**实测踩到过**） |
| **缓冲满即清空** | 防止 `len` 越界 | 数组溢出破坏相邻内存 |

### 4.6 验证

用真实碎片流做的端到端测试：

| 测试 | 结果 |
|---|---|
| 真实 32+32+7 碎片拼帧 | ✅ 拼出完整 71 字节帧 |
| 一次喂入完整帧 | ✅ |
| 垃圾前置（`=0,WL=80*8E`） | ✅ 垃圾被丢弃，后续正常 |
| 逐字节到达（79 次） | ✅ |
| 垃圾洪水 640 字节后恢复 | ✅ 无 `$` 即清空生效 |
| 半帧 + 补全 | ✅ |
| 连续 10 帧 | ✅ 10/10 全解析正确 |

## 5 软件设计

### 5.1 从机主循环

```
main()
 ├─ USART1_Init(9600)      调试串口
 ├─ LORA_Init(9600)        LoRa 模块
 ├─ Beep_Init / Led_Init
 ├─ LORA_ReadConfig        读配置（确认模块在线）
 ├─ LORA_ReadVersion       读版本
 ├─ LORA_SetConfig         写配置（与主机一致）
 ├─ Report_Init            传感器初始化
 └─ while(1)
     ├─ tick >= 1000ms ?
     │   ├─ Report_Once()  采集→组帧→发送→打印
     │   └─ Led0_Toggle
     ├─ USART3_TakeFrame → USART1 转发（LoRa→PC）
     ├─ USART1_TakeFrame → LORA_SendData（PC→LoRa）
     └─ delay_ms(10); tick += 10
```

**周期计时修正**（`main.c` 的 `[FIX-DBG4]`）：

```c
tick -= REPORT_INTERVAL_MS;      // 保留溢出余量
Report_Once();
tick += REPORT_COST_ESTIMATE_MS; // 补偿上报阻塞的 ~300ms
```

### 5.2 主机主循环

```
main()
 ├─ USART1_Init(9600)
 ├─ LORA_Init(9600)
 ├─ Beep_Init / Led_Init
 ├─ LORA_ReadConfig / ReadVersion / SetConfig
 ├─ FrameAsm_Reset          清拼帧缓冲
 ├─ Master_Init             OLED 初始化 + 显示"等待从机"
 └─ while(1)
     ├─ USART3_TakeFrame ?
     │   └─ while FrameAsm_Push ...   ← 流式拼帧
     │       └─ Master_ParseFrame ?
     │           ├─ showingWait = 0
     │           ├─ screenDirty = 1     ← 只标脏，不刷屏
     │           └─ Led0_Toggle
     ├─ USART1_TakeFrame → LORA_SendData（PC→LoRa）
     ├─ idleMs >= 5000 ?               ← 断线保护
     │   └─ 显示等待 + 清报警 + 关蜂鸣器
     ├─ screenMs += 10
     ├─ 报警跳变 ? → 立即蜂鸣器 + 立即刷屏   ★不遵循周期
     ├─ screenMs >= 10000 && dirty ? → Master_Display()
     └─ 报警中 ? → 蜂鸣器每 500ms 翻转
```

### 5.3 数据与显示解耦

**核心思想**：数据更新和屏幕刷新是两个独立的事。

| | 更新频率 | 触发者 |
|---|---|---|
| **数据**（`master_data`） | 每秒（每收到一帧） | `Master_ParseFrame()` |
| **屏幕**（OLED） | 每 10 秒 | `Master_Display()` |

```c
/* 收帧：只更新数据，不碰屏幕 */
if (Master_ParseFrame(s_rxBuf, rxLen)) {
    screenDirty = 1;          // 标记"有新数据待显示"
}

/* 10 秒定时：才真正渲染 */
if (screenMs >= SCREEN_REFRESH_MS && screenDirty && !showingWait) {
    screenMs = 0;
    screenDirty = 0;
    Master_Display();         // 渲染当前最新数据
}
```

**好处**：数据始终最新，屏幕不闪。

### 5.4 报警为什么是例外

报警不能等 10 秒 —— 水位超限要立刻知道。

用**边沿触发**（检测状态跳变）：

```c
if (master_data.waterAlarm != prevAlarm)     // 状态变了
{
    prevAlarm = master_data.waterAlarm;

    if (master_data.waterAlarm) {
        beepOn = 1;
        Beep_Ctrl(1);                        // 立即响，不等 500ms 计时
    } else {
        beepOn = 0;
        Beep_Ctrl(0);                        // 立即停
    }

    if (!showingWait) {
        screenMs = 0;
        Master_Display();                    // 立即刷屏
    }
}
```

**为什么用边沿而不是电平**：
- 电平触发 → 报警期间每轮循环都刷屏 → OLED 疯狂闪烁
- 边沿触发 → 只在跳变瞬间刷一次，报警持续期间屏幕稳定

### 5.5 断线保护

5 秒没收到数据 → 显示"等待从机" + **必须清报警**：

```c
master_data.waterAlarm = 0;
prevAlarm = 0;
beepOn = 0;
beepMs = 0;
Beep_Ctrl(0);
```

> **不清理的后果**：如果断线前正在报警，`waterAlarm` 会保持 1，蜂鸣器**无限期长响**。
> 这是实测发现的 bug。

## 6 数据流与时序

### 6.1 正常时序（水位正常）

```
t=0s     从机采集 → 组帧 → LoRa 发送
t=0.08s  主机收到碎片 → 拼帧 → 解析 → master_data 更新，screenDirty=1
t=1s     从机第 2 帧 ...
...
t=10s    主机 screenMs >= 10000 → Master_Display() → OLED 刷新
t=20s    OLED 再次刷新
```

屏幕每 10 秒刷新，但数据每秒都在更新。

### 6.2 报警时序

```
t=25.0s  从机发出 WL=75（超阈值 70）
t=25.0s  主机解析 → waterAlarm 0→1（跳变！）
         ├─ Beep_Ctrl(1)      立即响
         └─ Master_Display()  立即刷屏 → "水位:75%!" + "水位过高"
t=25.5s  蜂鸣器翻转（500ms 计时）
t=26.0s  蜂鸣器再翻转 ...
...
t=35.0s  常规 10 秒周期刷屏（报警状态持续）
```

**报警响应延迟 < 100ms**（取决于串口收帧速度），远小于 10 秒刷新周期。

### 6.3 断线时序

```
t=0s     最后一帧到达
t=1s     idleMs=1000
...
t=5s     idleMs >= 5000 → 显示"等待从机"
                         清 waterAlarm
                         关蜂鸣器
t=6s     从机恢复发送 → 收到帧 → 正常显示
```

## 7 设计取舍汇总

| 决策点 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| **通信** | LoRa 470MHz 私有链路 | WiFi / 蓝牙 / LoRaWAN | 距离够、功耗低、无需公网、无需网关 |
| **协议** | ASCII 文本帧 | 二进制 TLV | 对端串口助手可直接读，调试成本低；帧长 71 字节对 LoRa 不是瓶颈 |
| **可靠性** | 校验和丢弃坏帧，靠周期冗余 | ACK + 重传 | 数据周期重复，丢一帧损失 1 秒；重传要开接收窗，功耗和复杂度都上升 |
| **帧同步** | 按 `\r\n` 流式拼帧 | 定长帧 / 长度前缀 | LoRa 模块分块吐数据，只能按行边界重组 |
| **显示** | 数据与显示解耦（10 秒） | 每帧都刷屏 | OLED 频繁刷新会闪烁 |
| **报警** | 边沿触发立即刷屏 | 电平触发 / 等周期 | 报警要快；边沿触发避免持续闪烁 |
| **水位** | 非线性门限表 + 噪声死区 | 线性换算 | 传感器输出与液位非线性；死区消除干燥噪声误报 |
| **ADC** | 寄存器直操 | 标准库封装 | 标准库路径下 EXTTRIG/SWSTART 时序不明确，实测转换不启动 |
| **缓冲** | 静态区（.bss） | 栈上 | 栈只有 1KB，DHT20 调用层级深，栈上放 256B 缓冲有溢出风险 |

## 8 已知限制

| 限制 | 说明 | 影响 |
|---|---|---|
| **单向数据流** | 从机→主机单向；主机可发但固件未用于控制从机 | 无法远程配置从机 |
| **无应答重传** | 透明传输，丢帧不重传 | 偶发 1 秒数据空白 |
| **无时间戳** | 帧内不含时间 | 主机无法判断数据新鲜度（靠 5 秒超时兜底） |
| **水位量程固定 90mm** | 门限表按 90mm 标定 | 换传感器需重新标定门限表 |
| **单信道** | 所有节点同一信道 | 多从机需分时或分信道 |
| **主机保留从机代码** | `sensor_report.c` 等在主机工程中但未使用 | 仅占 Flash，不影响功能 |
| **无低功耗设计** | 从机 1 秒一帧，全程运行 | 需市电或大容量电池，不适合长期电池供电 |
